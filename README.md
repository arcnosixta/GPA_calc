# Техническое задание — ScholarPath

**Версия документа:** 1.0 (проект)  
**Заказчик / продукт:** учебное командное веб-приложение ScholarPath  
**Команда:** 4 человека (назначить имена в таблице)  
**Платформа:** браузер, desktop + mobile; Next.js  
**Цель первого этапа:** согласовать ТЗ, зоны ответственности, критерии приёмки; затем приступить к разработке MVP.

## 1. Проблема и цель

Студентам сложно оценивать академический прогресс при разном количестве кредитов на предметах. Ручные расчёты GPA и прогнозов отнимают время и создают ошибки.

**Цель:** разработать доступное веб-приложение для учета предметов, расчета GPA, анализа динамики по семестрам и моделирования будущих оценок. Сайт должен быть простым в использовании и полезным многократно на протяжении учёбы.

**Референс:** предоставленный скриншот «Academic Performance», содержащий боковую навигацию, карточки Cumulative GPA / Total Credits / Honors Track, GPA History и Grade Simulator.

### 1.1 Границы

**В MVP:** локальные данные одного пользователя в одном браузерном профиле, без регистрации, серверной БД и пользовательских ролей. В команде при этом есть 4 **разработческие** роли.

**Вне MVP:** вход через университетские системы, автоматическое получение оценок, интеграции PlatOnus, ИИ, онлайн-синхронизация, транскрипт с юридической силой, оплата, реальные университетские правила выдачи диплома с отличием.

## 2. Пользовательские сценарии

- **UC-01. Первый запуск:** вижу краткое пояснение, могу загрузить демо-данные или создать первый семестр.
- **UC-02. Добавить дисциплину:** указываю название, семестр, кредиты и оценку; вижу новый GPA.
- **UC-03. Изменить оценку:** редактирую предмет и немедленно получаю обновлённый расчёт.
- **UC-04. Просмотр прогресса:** вижу общий GPA, завершённые кредиты, цели и историю по семестрам.
- **UC-05. Смоделировать результат:** задаю предполагаемые оценки по будущим предметам, наблюдаю прогноз без изменения настоящих данных.
- **UC-06. Оценить цель:** ввожу желаемый итоговый GPA и оставшиеся кредиты, вижу необходимый средний GPA и предупреждение о недостижимости.
- **UC-07. Резервное копирование:** скачиваю JSON своих данных и могу восстановить их в другом браузере через импорт.
- **UC-08. Настройка:** задаю всего кредитов в учебном плане, целевой GPA и шкалу (фиксированная 4.0 в MVP; расширение позже).

## 3. Структура интерфейса

### 3.1 Общие элементы

- **Sidebar:** Dashboard, Subjects, Semesters, Simulator, Settings. На мобильных — компактная навигация.
- **Header:** название раздела, краткий текст, действия «Импорт/Экспорт» в настройках.
- **Состояния UI:** loading/hydration, empty, success, validation error, unavailable-to-calculate.

### 3.2 Dashboard

1. **Cumulative GPA:** крупный показатель, например `3.60 / 4.00`; сравнение с целью (не только декоративная метка «On Track»).
2. **Total Credits:** `завершено / план`; прогресс-бар (план кредитов указывается пользователем).
3. **Goal Track:** `текущий GPA → целевой GPA`; прогресс, требуемый средний GPA при известных оставшихся кредитах. Надпись **«Cum Laude»** не присваивается автоматически без правил конкретного университета; заменяем на «Цель GPA».
4. **GPA History:** точки GPA по семестрам и/или накопительного GPA; легенда явно различает эти показатели; целевая линия.
5. **Grade Simulator:** список будущих курсов, выбор оценок, мгновенная оценка влияния на прогноз.

### 3.3 Subjects / Semesters

- Название предмета — обязательная строка (1–100 символов).
- Кредиты — положительное число; для MVP целое 1–30 (позже можно разрешить дробные).
- Оценка — выбор из единой конфигурируемой таблицы; «ещё не получена» допускается для планируемого предмета, но не входит в *текущий* GPA.
- Семестр — обязательная принадлежность предмета.
- CRUD: добавление, редактирование, удаление; перед удалением — подтверждение.
- Список сортируется по семестру, затем по названию; есть пустые состояния.

### 3.4 Simulator

- Создать набор будущих предметов или выбрать предметы со статусом «планируется».
- Выбрать прогнозируемую оценку для каждого.
- Показывать **текущий GPA**, **прогнозируемый GPA** и **разницу**.
- Переключение оценок в симуляторе не меняет сохранённые полученные оценки.
- Отдельная кнопка для применения выбранных оценок, если команда решит включить её; по умолчанию MVP симулятор только прогнозирует.

## 4. Модель данных

```ts
type GradeCode = 'A' | 'A-' | 'B+' | 'B' | 'B-' | 'C+' | 'C' | 'C-' | 'D+' | 'D' | 'F';

type Semester = {
  id: string;
  name: string;       // Например, «1 курс · осень 2026»
  order: number;      // Порядок на графике
};

type Subject = {
  id: string;
  semesterId: string;
  name: string;
  credits: number;
  grade: GradeCode | null; // null = ещё не получена
};

type Settings = {
  targetGpa: number;          // 0..4
  totalProgramCredits: number; // План всех кредитов (>=0)
  gradeScaleId: 'default-4';
};

type ScholarData = {
  version: 1;
  semesters: Semester[];
  subjects: Subject[];
  settings: Settings;
};
```

**Оценочная шкала MVP (предположение, не официальный стандарт для всех вузов):** A=4.0, A-=3.7, B+=3.3, B=3.0, B-=2.7, C+=2.3, C=2.0, C-=1.7, D+=1.3, D=1.0, F=0.0. Шкала согласуется командой до реализации; при необходимости её можно заменить под требования конкретного вуза.

**Важно:** кредиты с оценкой `null` не входят в текущий GPA и завершённые кредиты. Приложение не пытается автоматически интерпретировать пересдачи, «W», «P/F», transfer credits и исключения; это отдельные будущие правила.

## 5. Математика и бизнес-правила

**Общий GPA:** `sum(gradePoint(subject.grade) * subject.credits) / sum(subject.credits)` — только по предметам с выставленной оценкой.

**GPA семестра:** то же вычисление, но лишь для дисциплин указанного семестра.

**Прогноз GPA:** `(текущая взвешенная сумма + взвешенная сумма прогнозов) / (завершённые кредиты + кредиты прогнозируемых дисциплин)`.

**Требуемый средний GPA для цели:** `required = (target * (completed + remaining) - currentGpa * completed) / remaining`, если `remaining > 0`.

- `required > 4.0`: цель недостижима при заданном количестве оставшихся кредитов (при шкале 4.0).
- `0 <= required <= 4`: цель математически достижима; фактическая возможность составить нужную комбинацию буквенных оценок проверяется отдельно.
- `required < 0`: цель уже обеспечена даже при нулевом среднем по оставшимся кредитам в рамках формулы.
- `remaining = 0`: показывать итог без деления на ноль; текущий GPA уже является итогом этой модели.
- `completed = 0`: текущий GPA отсутствует (`—`), а не `0.00`.
- Никаких значений `NaN`, `Infinity` в интерфейсе; округление только для отображения (до 2 знаков), внутри расчётов сохраняется точность.
- Ожидаемый максимум GPA — 4.0 в базовой шкале.
- Показатель «всего кредитов» должен различать **план программы**, **оценённые кредиты** и **запланированные кредиты**; нельзя смешивать их.

**Проверочный пример:** текущий GPA 3.20 при 60 завершённых кредитах, ещё 30 кредитов и цель 3.50 → необходимо `(3.50*90 - 3.20*60)/30 = 4.10`; цель невозможна при максимуме 4.0, достижимый максимум `(3.20*60 + 4*30)/90 ≈ 3.47`.

## 6. Архитектура и границы модулей

```text
src/
  app/                     # Next.js routes, layout
  components/ui/           # общие UI элементы
  features/dashboard/      # карточки и графики
  features/subjects/       # список и форма дисциплин
  features/semesters/      # раздел семестров
  features/simulator/      # экран и элементы прогнозирования
  features/settings/       # предпочтения
  domain/                  # типы, оценки, чистые формулы
  application/             # use cases, orchestration
  infrastructure/storage/  # localStorage repository, import/export
  tests/
```

**Правила:**

1. `domain` не импортирует React, Next.js и браузерные API.
2. `application` использует функции домена и интерфейс репозитория.
3. `infrastructure` реализует интерфейс репозитория; только здесь прямой доступ к `window.localStorage`.
4. UI вызывает прикладные сценарии; не содержит копий GPA-формул.
5. Интеграция между участниками — через согласованные типы и публичные функции, без взаимного изменения чужих модулей без PR.

**Пример контрактов (уточняются в Sprint 0):**

```ts
interface ScholarRepository {
  load(): ScholarData | null;
  save(data: ScholarData): void;
}

function calculateGpa(subjects: Subject[]): number | null;
function calculateRequiredGpa(currentGpa: number, completedCredits: number, remainingCredits: number, targetGpa: number): number | null;
function simulateGpa(completed: Subject[], planned: Subject[]): number | null;
```

## 7. Нефункциональные требования

- **UX:** понятные подписи и подсказки; ключевые действия доступны не более чем за несколько шагов от Dashboard.
- **Responsive:** 360px и шире, без горизонтальной прокрутки на основных экранах.
- **Accessibility:** читаемый контраст, метки у полей, фокус клавиатуры, текстовые альтернативы графикам, не полагаться только на цвет.
- **Данные:** автоматическое сохранение после подтверждения изменений; JSON экспорт и импорт с валидацией структуры/версии; импорт требует подтверждения замены текущих данных.
- **Приватность:** данные остаются в браузере, пока пользователь сам не экспортирует их; предупреждение, что очистка браузера удалит localStorage.
- **Надёжность:** отсутствие крашей при пустых данных, неправильном JSON, нулевых кредитах, некорректных значениях.
- **Тесты:** Vitest для формул, правил и сценариев; ручная проверка главных пользовательских путей.
- **Сборка:** `npm run build` проходит; отсутствие TypeScript-ошибок; ESLint настроен.

## 9. Взаимодействие и GitHub-процесс

- Ветки: `main`, `feature/layout`, `feature/dashboard-ui`, `feature/gpa-engine`, `feature/storage-crud` и далее небольшие тематические ветки.
- Задача GitHub Issue должна иметь: описание, владельца, чек-лист, критерии готовности, зависимость.
- Один PR = логически завершённая часть. Автор проверяет локальную сборку; другой участник делает review.
- **Definition of Done (DoD):** код типизирован, нет ошибок сборки, тесты для бизнес-логики, ручная проверка сценария, PR просмотрен, документация обновлена при изменении поведения.
- Единые кодовые соглашения: TypeScript strict, понятные имена, без `any` без обоснования.
- Конфликты в доменных типах/контрактах решаются совместно до объединения PR.

## 11. Приёмочные тест-кейсы

| ID | Действие | Ожидаемый результат |
| --- | --- | --- |
| AT-01 | Добавить A (4.0), 3 кредита и B (3.0), 2 кредита | GPA = `(4*3+3*2)/5` = **3.60** |
| AT-02 | Добавить предмет с `grade=null`, 5 кредитов | Текущий GPA не меняется |
| AT-03 | Поменять B (3.0) на A (4.0) | GPA обновляется до **4.00** |
| AT-04 | Создать семестры в порядке 1, 2, 3 | Точки истории расположены в правильном порядке |
| AT-05 | Выполнить симуляцию будущего A (4.0) | Видна новая цифра прогноза, исходные сохранённые оценки без изменений |
| AT-06 | При GPA 3.20/60 кредитов, цель 3.50 и 30 оставшихся | Требуется **4.10**, статус «невозможно», максимум ≈**3.47** |
| AT-07 | Обновить страницу | Данные и настройки сохраняются |
| AT-08 | Импортировать ошибочный JSON | Понятная ошибка; прежние данные не повреждены |
| AT-09 | Открыть приложение с пустым хранилищем | Подсказка «Добавьте первый семестр», нет падения |
| AT-10 | Открыть на ширине 360px и пользоваться с клавиатуры | Нет критической горизонтальной прокрутки, формы доступны |

## 12. Риски и решения

| Риск | Снижение риска |
| --- | --- |
| Разные шкалы университетов | Для MVP явная шкала 4.0, не утверждать универсальность |
| Неверное понимание «Honors Track / Cum Laude» | Заменить на личную цель; правила наград добавлять только с настройкой вуза |
| Потеря localStorage | Кнопка резервной копии JSON и предупреждение об очистке браузера |
| Несогласованные интерфейсы модулей | Зафиксировать типы и контракты до параллельной разработки |
| Чрезмерно большой scope | Строго отделять MVP от V1.1 и будущих функций |
| Устаревшая картинка вместо работающей панели | Запретить декоративные значения, которые не связаны с реальными данными |

## 13. Что нужно утвердить на командной встрече

- ФИО каждого из четырёх участников и окончательное распределение ролей.
- Шкалу GPA вашего учебного заведения и трактовку повторных/неоцениваемых дисциплин.
- Считать «оставшиеся кредиты» от общего плана или вводить вручную (рекомендация: по плану, с ручной корректировкой в симуляторе).
- Нужен ли русский интерфейс в MVP или сразу русский + казахский.
- Есть ли у команды срок сдачи и обязательные технологии/критерии преподавателя.

**Финальное условие запуска:** все четыре участника согласовали свой раздел, примеры расчётов проверены вручную, и после этого начинается программирование.
