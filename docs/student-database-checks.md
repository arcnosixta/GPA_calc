# Auth и личные данные: реализация Акылбека

Дата: 25 ноября 2026. База: `2f338c9` (`main`, fast-forward с чистого checkout).
По прямому указанию пользователя работа выполнена в `main`, с commit и push.

## Что подключено

- `/login`, `/register`, `/verify-email`, `/forgot-password`, `/reset-password`, `/logout`: общие Supabase SSR/browser clients, реальные Auth API, ожидание письма, неверные данные, истёкшая ссылка и сетевые ошибки. Привилегированные роли в формах отсутствуют.
- `/auth/callback`: PKCE code exchange и token hash confirmation (signup/email/recovery). Переход только на `/dashboard` или `/reset-password`; произвольные внешние next URL не используются. Ответы не кэшируются.
- `/dashboard`: проверенный `/api/backend/account`, загрузка сеанса, отдельная ошибка 503, onboarding имени/фамилии/вуза/группы, сводка GPA и календарь из каталога.
- `/profile`: чтение аккаунта из backend и сохранение разрешённых полей текущего Auth-пользователя. Вуз определяется через программу группы; принадлежность проверяется перед записью.
- `/setup`, `/subjects`, `/subjects/[subjectId]`: личные строки `student_subjects`, каталог без архивных предметов, рекомендации группы, повторное добавление возвращает существующую запись. Снимки названия и кредитов берутся из БД. Групповые рекомендации добавляются по одному с явным подтверждением.
- Баллы: null отличается от 0, предварительный расчёт использует существующий модуль JS. После сохранения читается `student_results`. SQL-ограничения не обходятся. INSERT, затем UPDATE только баллов при конфликте ключа: обычный upsert затрагивал бы закрытый UPDATE-grant ключевого столбца.
- Прогноз: отдельная `grade_forecasts`, сохранение и удаление предположения, пересчёт прогноза без изменения оценок. `/progress` показывает GPA по семестрам выбранного года.
- Календарь: фильтр по вузу профиля и выбранному учебному году, источники и статус из БД; пустой каталог не заменяется статическим шаблоном.

Новые репозитории: `src/lib/data/profile.ts`, `student.ts`, `errors.ts`, `mode.ts`.
Формы: `src/components/auth/supabase-*.tsx`.
Студенческий UI: `src/components/student/supabase-*.tsx`.
Миграции, RLS, seed, generated types, Proxy и общие Supabase-клиенты не менялись.

## Отдельный интеграционный срез режима

`NEXT_PUBLIC_DATA_MODE=supabase` включает реальный UI; отсутствие значения сохраняет прежний demo/localStorage UI. Наличие URL/key само по себе не включает реальный режим. Ошибка Supabase не переключает приложение в деморежим.

Минимальный патч общей оболочки для просмотра владельцем Куралом:

- `src/app/(workspace)/layout.tsx`: выбор `SupabaseWorkspace` вместо demo gate только в реальном режиме.
- `src/components/layout/auth-layout.tsx`: подписи аккаунта вместо надписей демоверсии в реальном режиме.

Этот патч выделен отдельным коммитом. Согласование с Куралом вне этой сессии и проверка Vercel Preview не выполнялись; автоматическая интеграция сделана по прямой просьбе пользователя работать в main. В настоящем режиме неподключённые разделы управления/чаты не отображают demo-данные под видом аккаунта.

Локально `.env.local` содержит переданные пользователем URL/key и `NEXT_PUBLIC_DATA_MODE=supabase`; файл игнорируется Git. Ключи в коммитах отсутствуют. В общих Preview/Production переменные не менялись.

Учебный год хранится в URL `?year=2026-2027` и личных записях. В схеме profiles нет поля выбранного периода; постоянное предпочтение периода в профиле требует отдельного согласованного изменения схемы.

## Что требуется для приёмки и запуска

1. В Supabase Auth разрешить `http://localhost:3000/auth/callback`, адрес тестового порта при необходимости и точный callback URL выбранного Preview/Production. Для восстановления разрешить callback с `?next=/reset-password`. Site URL должен соответствовать окружению.
2. Стандартные письма Supabase используют PKCE callback; открывать их нужно в браузере, начавшем регистрацию/восстановление. При использовании token hash шаблон ведёт на `/auth/callback?token_hash={{ .TokenHash }}&type=signup` либо `type=recovery`.
3. На согласованных двух тестовых аккаунтах проверить реальные signup/email, callback, login/logout, восстановление, перезагрузку и повторный вход, запись профиля/плана/баллов, изоляцию и ошибки сети. В этой сессии аккаунты и письма облака не изменялись: тестовые адреса/пароли не были предоставлены.
4. После приёмки включить режим на выбранном Vercel Preview, затем отдельно на общем развёртывании. В рамках этой работы развёртывание не выполнено.

Добровольный импорт localStorage **не включён**: по заданию он следует после приёмки пустого реального аккаунта, а транзакционного импортного RPC в основе нет. Предлагаемый контракт для Курала: `import_student_plan(request_id uuid, items jsonb)` с владельцем `auth.uid()`, подтверждёнными subject IDs, academic_year/semester, nullable rk1/rk2/exam и отдельным forecast; одна транзакция, серверный idempotency key и результат с количеством записей/конфликтами. До согласования контракта нельзя заменять его последовательностью браузерных записей. Локальные демоданные не изменяются.

Официальный контракт callback: [Supabase PKCE](https://supabase.com/docs/guides/auth/sessions/pkce-flow), [Next.js user management](https://supabase.com/docs/guides/getting-started/tutorials/with-nextjs).
