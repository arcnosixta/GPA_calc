# Акылбек — Auth и личные учебные данные в Supabase

Доступ к проекту для SDK настраивается файлом `.env.local`, который Курал передаст из `.env.team`. Он содержит только URL и publishable key. Личный вход в Dashboard владельца для работы приложения не требуется. Перед началом выполните `npm ci` и `npm run check:backend`. Персональные операции БД требуют отдельного настоящего Auth-аккаунта после подключения реальных форм входа. Порядок описан в разделе «Доступ участников к общей БД» файла `docs/database-plan.md`.

Ты работаешь как агент Kuat Akylbek, владельца UI/UX и студенческого frontend ScholarPath. Подключи реальную авторизацию и личные данные к основе PostgreSQL/Supabase, подготовленной Куралом. Начни от его согласованного SHA `main` в отдельной копии и ветке `student-database`. Прочитай `AGENTS.md`, README, `docs/database-plan.md`, миграции, generated types и актуальные формы. Перед изменениями проверь ветку и `git status`, сохрани работу коллег.

## Общая основа

- `@/lib/supabase/client` экспортирует `createBrowserSupabaseClient()`.
- `@/lib/supabase/server` экспортирует `createServerSupabaseClient()` для серверного кода с cookies.
- `@/lib/supabase/config` экспортирует `getSupabaseConfig()` и `isSupabaseConfigured()`.
- `@/lib/supabase/account` экспортирует серверный `getCurrentAccount(): Promise<{ user: User; role: AppRole; profile: Tables<'profiles'> } | null>`.
- `@/lib/database` экспортирует `AppRole`, `Tables`, `Insert`, `Update`. Каноническая схема типов находится в `src/lib/database.types.ts`.
- `GET /api/backend/account` возвращает проверенный аккаунт, `GET /api/backend/health` проверяет соединение и схему. Изучи фактический формат ответов и различай отсутствие входа и ошибку запроса.

У account endpoint HTTP 200 содержит `{ user: { id, email }, role, profile }`. HTTP 401 означает `unauthenticated`. HTTP 503 содержит `backend_unconfigured` или `account_unavailable`. Ответ 503 отображай как ошибку подключения. Серверная функция `getCurrentAccount()` возвращает полный объект `User`, а API выдаёт его ограниченное представление.

Курал отвечает за общие клиенты, cookie Proxy, схему и RLS. В реальном режиме ID пользователя берётся из валидированного Supabase Auth. Роль и область прав читаются из БД. ID, email и роль демосессии служат только текущему demo UI.

## Сначала заверши основной путь

1. Реализуй реальные `/login`, `/register`, подтверждение email/callback, выход и восстановление пароля. Используй общие клиенты. Настрой обработку успешного входа, ожидания подтверждения, неверных данных, истёкшей ссылки и сетевой ошибки. После реальной регистрации пользователь получает роль студента. Выбор привилегированной роли в реальных формах отсутствует.
2. После подтверждённого входа открой `/dashboard`. Если профиль требует заполнения, покажи диалог имени, фамилии, вуза и группы. Читай справочники из БД, проверяй принадлежность группы выбранному вузу и сохраняй профиль текущего пользователя. `/profile` читает сохранённые данные. Обновление страницы и новый вход восстанавливают их из серверного источника.
3. Подключи `/setup`, `/subjects`, `/subjects/[subjectId]` и учебную сводку к личным планам БД. Повторное добавление того же предмета в семестр даёт одну запись. Личные кредиты и исторические названия берутся из сохранённой записи. Архивированный предмет недоступен для нового выбора, существующая история сохраняется.
4. Сохраняй РК1, РК2 и экзамен текущего пользователя. Итоговая оценка и GPA после записи соответствуют SQL-правилам и JS-предпросмотру. Пустое значение отличается от нуля. Обрабатывай неполные баллы, FX и F по действующему README. После сохранения перечитай возвращённую запись или запроси обновлённые данные.
5. Подключи прогноз, календарь и `/progress` к согласованным таблицам и учебным данным. Прогноз хранит предположения отдельно от результатов. Календарь читается из общего каталога для вуза и периода, которые выбраны в профиле. Статический шаблон используется только как обозначенный демопример в соответствующем режиме.

Изучай реальные названия таблиц, RPC и ограничения по миграциям и generated types. Не создавай параллельную схему в клиенте. Если нужна транзакционная операция, которой нет в основе, передай Куралу контракт операции и конкретный сценарий, затем подключи согласованный RPC. Разделяй ожидаемую ошибку валидации, отказ RLS, истёкшую сессию и сетевой сбой.

## Переход режима — отдельный срез

Основа использует только `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Наличие этих двух значений разрешает подключение клиентов и backend-endpoint-ов. Текущий интерфейс продолжает demo/localStorage-сценарий.

После готовности Auth, профиля и личных данных реализуй явную границу режима и поддержку `NEXT_PUBLIC_DATA_MODE=supabase`. Согласуй её подключение в общей оболочке с Куралом и проверь на Preview. Активировать значение для общего развёртывания можно после приёмки полного пути. В выбранном реальном режиме ошибка Supabase показывает ошибку операции, а успешное сохранение подтверждается реальной записью. В demo-режиме действуют существующие данные браузера.

Реальный режим получает роль из проверенного аккаунта. Демо-переключатель не предоставляет полномочий в БД. Переходы и страницы должны учитывать восстановление сессии, отсутствие входа и незаполненный профиль. Проверку прав независимо выполняет RLS.

## Затем предложи добровольный импорт

Реализуй перенос localStorage только после приёмки первичного пути с пустым реальным аккаунтом. Перенос запускается отдельным действием пользователя. Покажи выбранный локальный профиль, список данных, ошибки формата и сопоставление предметов с существующим каталогом. Подтверждённые ID текущего каталога имеют приоритет. Старый email и локальная роль не определяют владельца или роль в БД.

Импорт выполняется от текущего Auth-пользователя, одной транзакционной операцией и с устойчивым ключом повторного выполнения. Повтор после сетевого сбоя не создаёт дубликаты и не портит уже сохранённые данные. Несопоставимые записи показывай пользователю до записи. Успех сверяй по серверному результату. Локальную копию сохраняй до подтверждённого завершения и сверки. Общий импортный RPC и ограничения согласуй с Куралом.

## Файлы и приёмка

Твоя область — Auth-страницы и `src/components/auth/**`, студенческие страницы и `src/components/student/**`, новые репозитории `src/lib/data/student.ts` и `src/lib/data/profile.ts`. При необходимости auth callback/confirm handler размещается в отдельном `src/app/auth/**` и согласуется с настройками redirect URL. Изменения shared layout/gate и общих серверных контрактов передавай Куралу отдельным согласованным патчем.

Миграции, RLS, seed, generated types, Supabase-клиенты, Proxy, общие переменные и зависимости принадлежат Куралу. Управление каталогом принадлежит Койшыману. Расчётные тесты и RLS-приёмка принадлежат Канату. Дополнительные изменения в этих областях сначала согласуй через Курала.

Сначала выполни проверки на локальной или выделенной тестовой среде. Реальные письма и изменения согласованных аккаунтов запускаются в рамках разрешённого тестового сценария. Ключи, пароли, cookies и токены не записывай в коммиты, промпты или отчёты. Окружение настраивается по `.env.example`.

Приёмка включает двух пользователей с раздельными данными, сохранение после перезагрузки и повторного входа, обработку ошибок, повтор добавления предмета, согласованность оценок/GPA и изоляцию прогноза. Импорт принимается отдельно с повтором одного запроса и намеренно повреждённой записью. Проверь 320/360 px и клавиатуру. Запусти `npm run lint`, `npm run build`, существующие тесты расчётов и согласованные DB-тесты.

В отчёте укажи базовый/итоговый SHA, файлы, какие сценарии уже используют БД, статус перехода режима и импорта, выполненные проверки и ограничения. Коммиты и описания пиши по-русски. Курал интегрирует изменения в `main`. Push рабочей ветки и PR выполняются по явному разрешению пользователя.
