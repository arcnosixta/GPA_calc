## Режим проверки и файлы

Перед проверкой запиши ветку, SHA и `git status`. Не переключай и не сбрасывай чужой checkout, не перезаписывай изменения коллег. Исходники, конфигурацию, зависимости, общие данные, реестр и чужую документацию не меняй. Отчёты и доказательства размещай только в `docs/qa-week/**`, например отдельной папке с датой и коротким SHA. Не добавляй пакеты и не меняй приложение ради теста.

Для браузерной проверки используй доступные инструменты и локальный сервер. Команды проекта: `npm run lint`, `npm run build`; для просмотра — `npm run dev` либо `npm start` после сборки. Не запускай конфликтующие серверы на уже занятом порту, не останавливай процессы коллег без согласования. Если проверка не выполнена, так и напиши, не ставь PASS по предположению.

## Что проверить

**Маршруты и граф ссылок.** На каждом из 29 URL проверь прямое открытие, ожидаемый заголовок, обновление и отсутствие 404/ошибок выполнения. Сверь реестр с существующими страницами и внутренними `href`: все назначенные экраны достижимы из главной или предусмотренной группы разделов, нет битых ссылок. Зафиксируй граф или таблицу «источник → ссылка → результат» для связей между разделами.

Отдельно пройди auth-путь: вход ↔ регистрация; вход → восстановление → сброс → вход; регистрация → пример подтверждения → вход. Проверь доступность профиля и экрана выхода через предусмотренные ссылки. У целей и симулятора есть возврат к прогрессу; у двух чатов — к списку; у задания — к соревнованиям; у подразделов управления — к управлению. Проверь браузерные «Назад»/«Вперёд», выделение текущего раздела и отсутствие дублированных оболочек.

**Мобильный экран.** Все 29 страниц проверь на ширинах **320, 360, 768, 1024, 1440 CSS px**. Запиши высоту окна и браузер. Нет горизонтального переполнения всей страницы, перекрытых полей и кнопок; таблица прокручивается внутри своего блока. Мобильное меню открывается и закрывается, переходы работают, скрытое меню не перехватывает фокус. Проверь длинные значения в формах там, где ввод реализован.

**Клавиатура и доступность.** Tab/Shift+Tab, видимый фокус, Enter/Space для соответствующих элементов, Escape для раскрываемого меню/диалога, понятный возврат фокуса после закрытия. Все формы имеют подписи; подсказки и ошибки связаны с полями. Проверь пустые обязательные поля, некорректный email, пароли и повтор там, где предусмотрена локальная валидация; кредиты проверяй по рабочим границам 1–30 и целочисленности. Не требуй настоящей проверки учётных данных.

**Данные и демочестность.** Исходный личный план — `math`, `programming`, `english`; A на 3 кредита, B на 2, предмет без оценки на 3. GPA `3.60`, в плане 8 кредитов, с оценкой 5, зачтено 5, прогресс 2 из 3. Каталог не должен стать личным планом, а «Без оценки» — нулём или F. Дополнительные моки будущих разделов явно обозначены как примеры.

Не должно быть ложного «Письмо отправлено», «Вход выполнен», «Пароль изменён», «Опубликовано», начисления баллов или доставленного сообщения. Auth-формы в исходной основе могут быть disabled/read-only: это честный каркас, но не готовый локальный UI. После доработки участником проверь заявленную валидацию и состояния, не ожидая сервера.

Локальные фильтры, формы и предпросмотры проверяй по их обещанному поведению: сброс, пустое состояние, снятие устаревшего результата, отсутствие мутации общих данных. После обновления страницы временное состояние может исчезать — постоянное сохранение не входит в задачу. Статическая сводка и примеры симулятора не должны выдавать себя за пересчёт изменённых оценок. Ссылка на управление не является серверной проверкой прав. Рейтинг не выдаёт личный самостоятельно введённый GPA за подтверждённую основу соревнования.

**Ошибки и команды.** Зафиксируй ошибки JS и сообщения консоли, результаты `npm run lint` и `npm run build`, выполненные действия и проверенный SHA. Отчёт другого агента — только подсказка для воспроизведения. Если сборка или доступ к браузеру недоступны, это ограничение проверки, а не успех.

Один скриншот не доказывает проверки всех размеров; отмечай только фактически просмотренные состояния.

Проверки готовых частей начинай 3–6 ноября; **7 ноября** — полная проверка интеграции, **8 ноября** — перепроверка исправлений. При смене SHA точно укажи, какие результаты относятся к какой версии. Коммиты и описания отчётов — по-русски; push только после явного разрешения пользователя, PR без запроса не создавай. Обычный отчёт в текущем чате — достаточная передача результата команде без отправки внешних сообщений.

Финальный вывод должен говорить, какие UI можно демонстрировать и какие маршруты ещё не готовы. Не объявляй завершение backend, запуск будущих продуктовых этапов или готовность всего MVP по факту существования страниц.
