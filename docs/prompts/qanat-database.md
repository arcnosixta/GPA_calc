# Канат — SQL/JS-расчёты, права и интеграция Supabase

Доступ к проекту для SDK настраивается файлом `.env.local`, который Курал передаст из `.env.team`. Он содержит только URL и publishable key. Личный вход в Dashboard владельца для работы приложения не требуется. Перед началом выполните `npm ci` и `npm run check:backend`. Персональные операции БД требуют отдельного настоящего Auth-аккаунта после подключения реальных форм входа. Порядок описан в разделе «Доступ участников к общей БД» файла `docs/database-plan.md`.

Ты работаешь как агент Qanat Qalmurzayev, владельца бизнес-логики, тестов и QA ScholarPath. Проверь PostgreSQL/Supabase-основу Курала и интеграцию участников на конкретном SHA. Начни от его базового коммита в отдельной копии и ветке `database-qa`. Прочитай `AGENTS.md`, README, `docs/database-plan.md`, миграции, RLS, generated types, текущий модуль оценивания и существующие тесты. Зафиксируй `git status` и среду.

## Что предоставляет основа Курала

- Общие `createBrowserSupabaseClient()` и `createServerSupabaseClient()` находятся в `@/lib/supabase/client` и `@/lib/supabase/server`.
- Серверный `getCurrentAccount()` находится в `@/lib/supabase/account` и возвращает проверенные `{ user, role, profile } | null`.
- `@/lib/database` экспортирует `AppRole`, `Tables`, `Insert`, `Update` по generated `src/lib/database.types.ts`.
- `GET /api/backend/health` проверяет соединение через `backend_health`, `GET /api/backend/account` проверяет текущий аккаунт.
- Основа настраивается через `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Перевод UI на `NEXT_PUBLIC_DATA_MODE=supabase` выполняют после готовности среза Акылбека. Наличие двух ключей само по себе оставляет UI в явном деморежиме.

Проверяй отдельно готовность схемы, готовность соединения и готовность пользовательских экранов. Ответ health endpoint подтверждает только свой узкий сценарий.

## Расчёты и сохранённые записи

1. Добавь регрессию на РК1 `4.1`, РК2 `66.1`, экзамен `8.6`: математический итог `24.50`, серверное округление даёт `25 / FX`. В текущем JS есть ошибка представления дробей, её нужно устранить по согласованному тесту. Сравни результаты SQL и действующего JS-модуля на обеих сторонах границ шкалы, FX, F, нуле, пустом поле, частичном и полном наборе РК1/РК2/экзамена. Веса и округление должны соответствовать согласованным миграциям и текущему README. Фиксируй воспроизводимый вход и ожидаемый выход.
2. Проверь взвешенный GPA и зачтённые кредиты. A на 3 кредита и B на 2 дают `3.60`. F на 3 и B на 2 дают `1.20`. Предмет без оценки исключён из знаменателя. FX и F входят в GPA, а зачёт кредитов следует рабочей шкале. Округление GPA выполняется только при отображении.
3. Проверь сохранение сырых баллов, повторное чтение и предсказуемое поведение при неполном наборе. Клиентские поля итоговой буквы, числового эквивалента и владельца не должны позволять подменить защищённый серверный результат.
4. Изменение каталожного названия/кредитов и архивирование предмета сохраняют личную историю. Прогноз хранится отдельно от фактических баллов. Повтор после сбоя и параллельное добавление одного предмета в семестр сохраняют одну корректную запись.

Используй существующие Node-тесты и добавь необходимую DB-проверку. Входы для расчётов можно проверять SQL-fixture-ами внутри откатываемой транзакции в выделенной среде. Пример, полученный через привилегированное соединение, подтверждает расчёт, а проверка RLS требует запросов от конкретных Auth-пользователей.

## Прямые проверки доступа

Создай или используй согласованные тестовые аккаунты пользователя A, пользователя B, модератора и администратора. Роли назначаются владельцем или разрешённым административным сценарием. Обычные запросы тестов идут с publishable key и токеном соответствующего пользователя. Параметры доступа передаются через локальное тестовое окружение, вывод отчёта маскирует чувствительные значения.

| Проверка | Ожидание |
| --- | --- |
| Запрос личных планов/баллов без входа | Личные строки недоступны |
| A читает и меняет свои данные | Разрешённый сценарий работает |
| A запрашивает, меняет или удаляет запись B по известному ID | Запись B остаётся недоступной или неизменной |
| A пытается заменить owner/user ID своей записи на B | Операция отклонена ограничением или RLS |
| Студент меняет общий каталог, роль, назначения | Операция отклонена |
| Модератор меняет назначенную группу | Разрешённый сценарий работает |
| Модератор меняет чужую группу или назначает привилегии | Операция отклонена |
| Администратор выполняет предусмотренное назначение | Изменение видно и соответствует схеме |
| Повтор транзакционного действия/импорта | Нет дублей и частичного результата |

Для запрещённого UPDATE с пустым ответом отдельно проверь неизменность строки владельцем. Проверь INSERT и UPSERT, альтернативные ID и прямое обращение к разрешённым RPC. Различай отсутствие grant, отказ политики и скрытую RLS строку. Удостоверься, что тесты не используют service role вместо реального пользователя.

## Браузерная приёмка по готовым срезам

Сначала проверь текущую демонстрационную конфигурацию. Затем на тестовой конфигурации с принятым Supabase-режимом пройди регистрацию, подтверждение, вход, профиль, план, баллы, прогноз, обновление страницы, выход и новый вход. Повтори под B и сверь отсутствие данных A. Проверь истёкший вход, ошибку записи, прямые URL и мобильную ширину 360 px. Регистрационные письма и изменения аккаунтов выполняй только в разрешённом тестовом сценарии.

После отдельной реализации импорта Акылбеком проверь добровольный запуск, предпросмотр, неизвестные ID каталога, повреждённую запись, повтор операции и сетевой обрыв. Неподтверждённый импорт не меняет БД. Неуспешная транзакция сохраняет исходное состояние. Повтор успешного импорта даёт тот же набор данных. Старая локальная роль не переносит привилегии реального аккаунта.

Полный backend геймификации не входит в приёмку этого среза. Существующий макет проходит регрессию навигации как демонстрационный экран.

## Файлы и отчёт

Твоя область — `supabase/tests/**`, `tests/database/**`, согласованные `scripts/database-*.mjs` и `docs/qa-database/**`. Существующие тесты расчётов можно дополнить рядом с модулем. Миграции, RLS, seed, клиенты, generated types и Proxy принадлежат Куралу. Поведенческие исправления SQL или JS согласуй с ним на конкретном тесте. Страницы участников исправляют владельцы.

Запусти `npm run lint`, `npm run build`, существующие тесты маршрутов, оценивания и каталога, а также добавленные DB/RLS-тесты. Обозначь тесты, которые требуют живой БД, отдельным запуском. Используй разрешённую среду и воспроизводимые fixtures, очищая только созданные тестом данные. Если нет необходимых тестовых аккаунтов или доступа к БД, заверши доступные чистые проверки и явно перечисли оставшиеся проверки.

В отчёте запиши SHA, среду и целевой project reference, миграции, запущенные команды, результат каждой allow/deny-пары, примеры SQL/JS, браузерные шаги и известные ограничения. Публикуй скриншоты с вымышленными данными и без cookies, токенов или ключей. Для дефекта укажи шаги, ожидаемое/фактическое поведение, владельца и SHA перепроверки.

Коммиты и описания пиши по-русски. Курал интегрирует изменения в `main`. Push рабочей ветки и PR выполняются по явному разрешению пользователя.
