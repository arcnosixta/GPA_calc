# Койшыман — каталог и управление через PostgreSQL/Supabase

Ты работаешь как агент Nurdaulet Koishyman, владельца данных, форм и интерфейсов управления ScholarPath. Подключи каталог, учебные планы, календари, архив и админский UI ролей к БД в пределах согласованных прав. Начни от базового SHA Курала в отдельной копии и ветке `management-database`. Прочитай `AGENTS.md`, README, `docs/database-plan.md`, миграции, generated types и текущие компоненты. Проверь `git status` и сохрани изменения коллег.

## Общие контракты

Для браузерного доступа используй `createBrowserSupabaseClient()` из `@/lib/supabase/client`, для серверного — `createServerSupabaseClient()` из `@/lib/supabase/server`. `AppRole`, `Tables`, `Insert`, `Update` экспортируются из `@/lib/database` и следуют `src/lib/database.types.ts`.

На сервере `getCurrentAccount()` из `@/lib/supabase/account` возвращает `{ user, role, profile } | null` после проверки пользователя. Клиентский экран использует предназначенный `GET /api/backend/account` либо данные серверного компонента. Изучи фактическую форму ответа. Техническая проверка схемы находится в `GET /api/backend/health`.

Два значения основы — `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Приложение использует publishable key и RLS вошедшего пользователя. Общую границу demo/Supabase-режима и `NEXT_PUBLIC_DATA_MODE=supabase` подключают Акылбек и Курал после приёмки Auth, профиля и студенческого пути. Подготовь data-репозитории для этого режима. Текущий demo-каталог продолжает работать до явного переключения.

## Подключи сценарии управления

1. На `/management` читай разрешённые предметы, кредиты, группы и семестры из БД. Подключи создание, редактирование, поиск и архивирование. Проверяй результат запроса и обновляй интерфейс по фактически сохранённой записи. Сохрани текущую валидацию и пустые состояния.
2. На `/management/universities`, `/management/programs`, `/management/groups`, `/management/semesters` подключи справочники и допустимые операции. Соблюдай связи направления с вузом и группы с направлением. Для семестров используй реальные значения и активность из согласованной схемы. Ошибки внешних ключей и конфликтов объясняй в форме.
3. На `/management/study-plans` работай со связями группы, семестра и предмета. Публикация и изменение состава используют транзакционный контракт схемы. Повтор одного действия даёт тот же состав без дублей. Архивные предметы исключены из новых выборов, прежние записи и их кредиты сохраняются.
4. На `/management/semesters` и соответствующем календарном UI читай и сохраняй календари с вузом, периодом, источником и областью применения. Студенческий `/progress` и форма баллов должны читать тот же источник через общий контракт. Согласуй его с Акылбеком через Курала.
5. На `/management/history` показывай разрешённый учебный архив вошедшего пользователя. Сохрани фильтры года/семестра, поиск и сортировку. Роль сотрудника сама по себе не раскрывает личные баллы других студентов. Применяй фактическую RLS-модель и допуски схемы.
6. На `/management/users` подключи разрешённые администратору роли и назначения модераторов. Роль берётся из серверного аккаунта. Выполняй назначение через разрешённую операцию базы. Поле профиля, пользовательские metadata и локальный переключатель роли не меняют полномочия реального аккаунта.

Работа модератора ограничена назначенными группами и областью, заданной схемой. Администратор управляет каталогом и назначениями в пределах контракта. Доступность UI согласуется с этими правилами. Проверь прямые запросы при участии Каната, потому что кнопка в интерфейсе не является границей доступа.

## Целостность и ошибки

Используемые предметы архивируй. Личные записи и зафиксированные кредиты сохраняются при изменениях общего каталога. Обновление справочника не должно незаметно перепривязывать чужие учебные записи. Для взаимосвязанных изменений используй согласованный RPC/транзакцию. Если такой операции нет в основе, передай Куралу пример и ожидаемый контракт до реализации.

Различай ошибку валидации, конфликт, отсутствие записи, отказ RLS и сетевой сбой. Пустой результат запроса не всегда означает успех UPDATE. Перечитай возвращённую запись или требуй подтверждённый изменённый ID. Формы могут повторить запрос после ошибки без дублирования результата. Удаление и архивирование требуют ясного пользовательского действия.

## Файлы и проверка

Твоя область — `src/app/(workspace)/management/**`, `src/components/management/**`, новые репозитории `src/lib/data/catalog.ts`, `src/lib/data/calendars.ts`, `src/lib/data/admin.ts`. Используй существующие стили и общие компоненты. Миграции, RLS, generated types, Supabase-клиенты, Proxy, seed, общая конфигурация и зависимости принадлежат Куралу. Изменения профиля и личных баллов принадлежат Акылбеку. Дополнительные shared-изменения передавай Куралу отдельным запросом.

Первый администратор назначается владельцем БД вручную для UUID уже зарегистрированного Auth-пользователя. Сценарий регистрации и seed оставляют эту операцию владельцу. Привилегированный ключ для клиентского UI не используется. Ключи, пароли, cookies и токены не записывай в отчёт и коммиты.

Проверь студента, модератора и администратора, разрешённую и чужую группу, повтор записи, архивирование предмета с оценённой личной записью, сохранение источника календаря и совпадение его отображения на студенческой стороне. Отдельно проверь попытку назначить роль обычным пользователем через API. Используй тестовую среду и согласованные аккаунты. После изменения прочитай данные повторно и перезайди в аккаунт.

Запусти `npm run lint`, `npm run build`, существующие каталожные тесты и согласованные проверки RLS. В отчёте укажи базовый/итоговый SHA, файлы, какие разделы подключены, результаты ролей и целостности, ограничения. Коммиты и описания пиши по-русски. Курал интегрирует изменения в `main`. Push рабочей ветки и PR выполняются по явному разрешению пользователя.
