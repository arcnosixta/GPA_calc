# ScholarPath — подключение PostgreSQL через Supabase

Команда подключает PostgreSQL в проекте Supabase **ScholarPath** (`hygmzyylxejrvobrvcwm`) в выбранном контексте Primary / Nurdaulet. Выбран бесплатный тариф и регион Europe Frankfurt. Курал готовит основу базы и серверного доступа. Акылбек и Койшыман подключают к ней свои пользовательские сценарии. Канат проверяет расчёты, права и интеграцию.

План следует зонам ответственности раздела 8 README. Текущая демоверсия остаётся доступна на время поэтапной миграции. Базовое подключение считается готовым после применения схемы, проверки политик, типов и соединения. Полный путь от регистрации до сохранённых баллов принимается отдельно после интеграции экранов участников.

## Таблицы и связи

В схеме 15 таблиц. Каталог состоит из `universities`, `programs`, `study_groups`, `subjects`, `semesters` и `study_plan_items`. Связь плана содержит свой семестр. Личная строка `student_subjects` имеет отдельный UUID и уникальность по студенту, исходному предмету, учебному году и семестру. `assessments` хранит сырые баллы, а представление `student_results` возвращает вычисленные оценку и числовой эквивалент. Для прогноза используется `grade_forecasts`.

`profiles`, `user_roles` и `moderator_groups` связываются с Supabase Auth. Календарь состоит из `academic_sources`, `academic_calendars` и `calendar_terms`. Предметы привязаны к направлению, планы — к группам того же направления. Перенос существующего предмета в другое направление выполняется отдельным согласованным процессом. Права на изменение родительских ID обычным клиентом отсутствуют.

Роль нового Auth-пользователя всегда `student`. Для назначения обычным пользователям роли `student` или `moderator` администратор вызывает `admin_set_user_role({ target_user_id, new_role })`. Группы модератора назначаются отдельными строками `moderator_groups`. Смена роли и назначение групп проверяются отдельно. Администратор не получает права чтения чужих личных оценок.

В `student_subjects` клиент вставляет только `subject_id`, `academic_year` вида `2026-2027` и `semester`. БД сама фиксирует владельца, название, код и кредиты активного предмета. По UUID личной строки выполняется upsert в `assessments`. При обновлении разрешены только `rk1`, `rk2`, `exam`, поэтому `student_subject_id` задаётся ключом запроса, а не изменяемым полем. Прогноз работает аналогично по UUID строки. Для исторического UI используются сохранённые личные записи и их `academic_year`, а не общая группа вымышленных студентов.

## Передача основы

Курал передаёт один базовый SHA, миграции, проверенный seed, TypeScript-типы БД, `.env.example` с именами переменных и документацию общих экспортов. Все участники начинают от этого SHA в отдельных копиях. Схема и сгенерированные типы определяют имена таблиц, столбцов и RPC. Формы и запросы используют эти имена напрямую через общий типизированный клиент.

| Файл | Общий контракт |
| --- | --- |
| `src/lib/supabase/config.ts` | `getSupabaseConfig()` и `isSupabaseConfigured()` |
| `src/lib/supabase/client.ts` | `createBrowserSupabaseClient()` для клиентских компонентов |
| `src/lib/supabase/server.ts` | `createServerSupabaseClient()` для серверного кода с cookies |
| `src/lib/supabase/account.ts` | `getCurrentAccount(): Promise<{ user: User; role: AppRole; profile: Tables<'profiles'> } \| null>` |
| `src/lib/database.types.ts` | Канонические generated types фактической БД |
| `src/lib/database.ts` | Типы `AppRole`, `Tables`, `Insert`, `Update` |
| `src/proxy.ts` | Обновление cookie-сессии |
| `GET /api/backend/health` | Публичная проверка схемы через `backend_health` |
| `GET /api/backend/account` | Проверенный аккаунт вошедшего пользователя |

Клиентский UI читает аккаунт через предназначенный endpoint или через серверный компонент. `getCurrentAccount()` вызывается на сервере. Значение `null` означает отсутствие подтверждённого аккаунта. Результат endpoint и ошибка запроса обрабатываются раздельно.

`/api/backend/account` отвечает HTTP 200 с `{ user: { id, email }, role, profile }`, HTTP 401 с `unauthenticated` при отсутствии входа и HTTP 503 с `backend_unconfigured` или `account_unavailable` при недоступной конфигурации/проверке. `/api/backend/health` отвечает HTTP 200 со статусом `ok` и маркером схемы `scholarpath-v1` либо HTTP 503 со статусом `unconfigured`/`unavailable`.

## Общие правила доступа

- Пользователь Supabase Auth связывается с данными через подтверждённый `auth.uid()`. Роль и область модератора читаются из разрешённого серверного источника. Поле формы и редактируемые пользователем metadata сохраняют только разрешённые данные профиля.
- Студент читает и меняет свои учебные записи. Группа, кредиты и предметы общего каталога меняются сотрудниками в разрешённой области. Администратор назначает роли и группы модераторов.
- Каждая доступная через Data API таблица имеет RLS и соответствующие grants. Проверки операций действуют при прямом запросе к API. Учётные данные владельца проекта используются для применения схемы и bootstrap, а обычные запросы приложения идут от вошедшего пользователя.
- Студенческие записи сохраняют собственные кредиты и исторические сведения. Архивирование предмета и изменение каталога сохраняют личные результаты. Повторное добавление предмета в тот же семестр обрабатывается ограничениями БД и согласованной операцией.
- Изменения, которые должны завершиться вместе, выполняются одной транзакционной операцией по контракту миграции. Предварительный SELECT в браузере служит для UX, а ограничения БД предотвращают дубли при параллельных запросах.

Правила grants и RLS, а также серверные клиенты с cookies описаны в официальной документации. [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) · [SSR-клиенты](https://supabase.com/docs/guides/auth/server-side/creating-a-client).

## Порядок внедрения

1. **Основа Курала.** Применить миграции в новый согласованный проект, проверить RLS, seed и типы. Проверить соединение endpoint-ом и сохранить фактический результат в отчёте.
2. **Auth Акылбека.** Настроить вход, регистрацию, callback/подтверждение, выход и восстановление доступа в поддерживаемом режиме подключения. После регистрации пользователь получает роль студента. Курал предоставляет проверенный серверный аккаунт.
3. **Профиль и каталог.** Акылбек сохраняет имя, фамилию, вуз и группу вошедшего пользователя. Койшыман подключает каталог и назначенные учебные планы. Канат проверяет разделение двух реальных тестовых аккаунтов и ролевой доступ.
4. **Баллы и учебные данные.** Акылбек подключает личные планы, РК1, РК2, экзамен, прогноз и прогресс. Проверяются запись, повторное чтение, перезагрузка и новый вход. Койшыман проверяет архив и календарные источники.
5. **Импорт демоданных.** После успешного базового пути пользователь отдельно выбирает перенос своих локальных записей. Акылбек показывает предпросмотр, проверяет формат и сопоставляет каталог с ID базы. Подтверждённый перенос выполняется транзакционно и повторно даёт тот же результат без дублей. Исходные локальные данные остаются доступны до подтверждённого завершения и сверки.
6. **Приёмка.** Канат повторяет прямые API-проверки политик и браузерный путь. Курал интегрирует коммиты, запускает общие проверки и фиксирует готовность каждого среза.

## Демо и подключённый режим

Основа использует две переменные — `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Они разрешают работу общих клиентов и backend-endpoint-ов. Текущий web UI продолжает явно обозначенный localStorage-деморежим. Само наличие ключей сохраняет этот выбор UI.

Акылбек реализует согласованный переход приложения. Поддержку `NEXT_PUBLIC_DATA_MODE=supabase` и активацию этого значения добавляет отдельным срезом после готовности Auth, профиля и студенческих данных. Значение для реального запуска выставляется после приёмки на тестовом окружении. При выбранном Supabase-режиме отсутствующая конфигурация или ошибка backend отображается как ошибка. В сообщениях о сохранении указывается источник результата, чтобы пользователь понимал, куда записаны данные.

Состояние соединения и готовность миграций проверяются отдельно от состояния входа. Endpoint проверки соединения возвращает ограниченный статус. Успех проверки подтверждает доступность БД, а регистрация, RLS и сохранение учебных записей проходят собственную приёмку.

## Настройка окружения и Vercel

1. Курал фиксирует project reference и целевой проект для миграций. Подключение каждого участника проверяется по этой записи.
2. Локальные значения `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` задаются в `.env.local` по `.env.example`. В репозиторий и промпты попадают только имена и пустые значения. Приложение использует publishable key. Привилегированный ключ для его обычных запросов не требуется.
3. В Supabase Auth настроить Site URL и разрешённые callback/восстановление для localhost и выбранного Vercel-домена. Реальная отправка писем проверяется на согласованных тестовых аккаунтах. [Настройка redirect URL](https://supabase.com/docs/guides/auth/redirect-urls).
4. Для Vercel задать две переменные основы в согласованных средах Preview и Production. После отдельной приёмки Акылбека включить `NEXT_PUBLIC_DATA_MODE=supabase` в нужной среде. Изменение переменных сборки требует новой сборки. Перед ней схема и seed целевой БД должны соответствовать коду.
5. После развёртывания проверить endpoint соединения, вход, обновление cookie-сессии, профиль, сохранение баллов и изоляцию аккаунтов. Персонализированные ответы и ответы с обновлением cookies сохраняют приватные правила кэширования из общей SSR-основы.

## Первый администратор

Сначала владелец регистрирует настоящий аккаунт через Auth. После появления его записи владелец БД выполняет отдельную ручную bootstrap-команду из основы Курала для конкретного UUID. В seed находятся только согласованные справочники. Автоматическое назначение администратора по email, форме регистрации или содержимому localStorage исключается из контракта.


В SQL Editor проекта владелец выполняет следующий блок после замены UUID на ID своего подтверждённого Auth-аккаунта. Команда допускает только первоначальное назначение. После появления администратора обычные назначения выполняются через защищённый `admin_set_user_role`.

```sql
do $$
declare
  account_id uuid := 'ВСТАВЬТЕ_UUID_ИЗ_AUTH_USERS'::uuid;
begin
  if exists (select 1 from public.user_roles where role = 'admin') then
    raise exception 'Первый администратор уже существует';
  end if;
  update public.user_roles set role = 'admin' where user_id = account_id;
  if not found then
    raise exception 'Auth-аккаунт и его запись роли ещё не созданы';
  end if;
end;
$$;
```

## Критерии приёмки команды

- Миграции применены к согласованному проекту, а generated types соответствуют схеме. Seed повторно выполняется без дублирования справочников.
- Browser и server используют общий набор клиентов. Сервер валидирует пользователя и получает роль из БД. Cookies восстанавливают вход после обновления.
- Два пользователя видят только свои планы, баллы, прогнозы и архив. Попытки прочитать, изменить или перепривязать чужую запись через API отклоняются политиками или ограничениями.
- Модератор работает в назначенных группах, администратор меняет разрешённые роли. Прямые запросы студента к каталожным изменениям и назначению ролей запрещены.
- Баллы и GPA совпадают в SQL/JS на базовом примере, FX, F, нуле, отсутствии и неполном наборе баллов. Повторное сохранение и добавление предметов не создают дубликаты.
- Ошибки сети, истёкший вход и валидация показываются в UI. Успешная запись подтверждена повторным чтением или возвращённой записью с корректным ID.
- `npm run lint`, `npm run build`, существующие тесты расчётов и новые DB/RLS-тесты проходят на одном интегрированном SHA. Отчёт указывает, какие проверки выполнены локально и на подключённом проекте.

Ветки участников — `student-database`, `management-database`, `database-qa`. Прямую интеграцию в `main` выполняет Курал. Коммиты и описания пишутся по-русски. Push и PR выполняются по явному разрешению пользователя.
